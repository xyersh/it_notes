
**Sync.Mutex** – это механизм синхронизации в Go, который используется для предотвращения гонок данных. Гонка данных возникает, когда несколько горутин одновременно пытаются получить доступ и модифицировать одни и те же данные. Это может привести к непредсказуемым результатам и ошибкам в программе.

### Зачем нужен Sync.Mutex?

- **Защита критических секций:** Мьютекс позволяет защитить блок кода (критическую секцию) так, чтобы только одна горутина могла выполнить его в данный момент времени.
- **Предотвращение гонок данных:** Гарантирует, что доступ к общим данным будет последовательным, а не параллельным, что устраняет возможность возникновения гонок данных.

### Правила использования sync.Mytex

- **Нулевое значение готово к использованию.** Мьютекс не нужно инициализировать. Нулевое значение `sync.Mutex` — это разблокированный мьютекс. Не пишите `mu := &sync.Mutex{}` или `new(sync.Mutex)`, просто объявите переменную: `var mu sync.Mutex`.
- **Никогда не копируйте мьютекс.** Мьютекс (как и любой примитив синхронизации) нельзя копировать. Если вы передаете структуру с мьютексом в функцию, передавайте её по указателю. Если вы копируете слайс структур с мьютексами — вы получите баг. Утилита `go vet` автоматически обнаруживает копирование мьютексов.
- **Всегда по возможности используйте `defer m.Unlock()`.** Это главное правило для предотвращения дедлоков. Если в критической секции произойдет `panic` или вы сделаете ранний `return`, мьютекс останется заблокированным навсегда.
```go
mu.Lock()
defer mu.Unlock()
// критическая секция
```
- **Держите критическую секцию минимальной.** Блокируйте только тот код, который обращается к разделяемым данным.
	>- _Плохо:_ Делать сетевые запросы (I/O), тяжелые вычисления или вызывать сторонние функции внутри `Lock/Unlock`.
	>- _Хорошо:_ Скопировать нужные данные в локальные переменные под локом, разблокировать мьютекс, и только потом работать с локальными переменными.
- **Используйте `sync.RWMutex` для read-heavy нагрузок.** Если ваша структура читается в 100 раз чаще, чем пишется, используйте `RWMutex`. Он позволяет множеству горутин одновременно читать данные (`RLock`), блокируя только на запись (`Lock`).
- **Защищайте состояние, а не операции.** Убедитесь, что _каждое_ чтение и _каждая_ запись защищаемой переменной находятся под блокировкой. Частая ошибка: защитить запись под мьютексом, но забыть защитить чтение в другом месте кода.
- **Избегайте вложенных блокировок (Nested Locks).** Захват нескольких мьютексов одновременно — прямой путь к дедлоку.
	>- _Правило:_ Если вам неизбежно нужно захватить несколько мьютексов (A и B), **всегда** захватывайте их в одном и том же порядке во всей кодовой базе (сначала A, потом B).
	>- _Альтернатива:_ Постарайтесь перепроектировать код так, чтобы использовать только один мьютекс.
- **Не встраивайте мьютекс анонимно.** Встраивание `sync.Mutex` в структуру делает её реализующей интерфейс `sync.Locker`, что может привести к случайному вызову `Lock()` из внешнего кода.
```go
// Плохо: внешний код может случайно вызвать myStruct.Lock()
type Counter struct {
    sync.Mutex 
    count int
}

// Хорошо: мьютекс скрыт, доступен только методам структуры
type Counter struct {
    mu    sync.Mutex
    count int
}
```
- **Всегда запускайте тесты с `-race`.** Флаг `go test -race` (или `go run -race`) включает детектор гонок (Race Detector). Это абсолютный мастхэв. Он находит 99% ошибок неправильного использования мьютексов и состояния гонки.
- **Используйте `go vet`.** Эта утилита проверяет код на синтаксические и логические ошибки, включая копирование мьютексов (`go vet ./...`).
- **Профилирование.** Если приложение работает медленно, используйте `pprof` (в частности, `go tool pprof -http=:8080 cpu.prof`), чтобы найти, не проводят ли горутины слишком много времени в ожидании блокировки мьютекса ( contention ).
- **Один мьютекс на группу связанных данных.** Если у вас есть несколько переменных, которые всегда меняются вместе (например, `width` и `height`), защищайте их одним мьютексом, а не заводите отдельный мьютекс на каждую переменную.
 - Методы которые используют мьютекс, как поле, должны иметь **ссылочные ресиверы**. Иначе блокировка не будет работать должным образом:
```go
 func(s *SomeStruct)SomeFunc(){
	 ...
 }
```
 - При преобладании операций чтения над изменением критического ресурса, следует использовать sync.RWMutex. Это позволить снизить нагрузку блокировок при чтении из ресурса. 
 



 
 ### Простой пример:

Представим, что у нас есть счетчик, который мы хотим увеличивать из нескольких горутин. Без синхронизации, значение счетчика может быть некорректным из-за гонок данных.

```go
package main

import (
        "fmt"
        "sync"
)

var (
        counter int
        mutex   sync.Mutex
)

func increment() {
        mutex.Lock()
        counter++
        mutex.Unlock()
}

func main() {
        var wg sync.WaitGroup
        for i := 0; i < 1000; i++ {
                wg.Add(1)
                go func() {
                        defer wg.Done()
                        increment()
                }()
        }
        wg.Wait()
        fmt.Println("Final counter value:", counter)
}
```

**Разбор кода**

1. **Объявление переменных:**
    - `counter`: Счетчик, который мы будем увеличивать.
    - `mutex`: Мьютекс для синхронизации доступа к счетчику.
2. **Функция increment:**
    - Захватывает мьютекс перед изменением счетчика.
    - Увеличивает значение счетчика.
    - Освобождает мьютекс.
3. **Основная функция main:**
    - Создает 1000 горутин, каждая из которых вызывает функцию `increment`.
    - Используется `sync.WaitGroup` для ожидания завершения всех горутин.

**Как работает:**

- Перед тем как изменить значение счетчика, горутина должна захватить мьютекс.
- Только одна горутина может владеть мьютексом в данный момент.
- После изменения значения счетчика, горутина освобождает мьютекс, позволяя другим горутинам получить к нему доступ.

**Благодаря использованию мьютекса, мы гарантируем, что значение счетчика будет увеличено на 1000, даже если к нему одновременно обращаются многочисленные горутины.**
