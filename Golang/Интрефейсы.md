## Назначение и философия интерфейсов
Интерфейс в Go — это **контракт поведения**. Он описывает _что_ должен уметь тип, но не _как_ он это реализует.

### Зачем нужны интерфейсы?
| Задача                 | Как решает интерфейс                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| **Слабая связанность** | Компоненты зависят от абстракции, а не от конкретных реализаций.                |
| **Полиморфизм**        | Одна функция может работать с разными типами, реализующими одинаковый контракт. |
| **Тестируемость**      | Легко подменять реальные зависимости моками/стабами.                            |
| **Расширяемость**      | Новый тип можно добавить без изменения кода, использующего интерфейс.           |


>💡 **Ключевая особенность Go:** Интерфейсы реализуются **неявно**. Не нужно указывать `implements`. Если тип имеет все методы интерфейса с совпадающими сигнатурами, он автоматически его реализует. Это называется _structural typing_.


## Синтаксис и базовые принципы

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```

### Основные правила

- Интерфейс может содержать только сигнатуры методов (начиная с Go 1.18 также поддерживает `type` constraints в дженериках).
- Значение интерфейса по умолчанию: `nil`.
- Вложенность (embedding): `type ReadCloser interface { Reader; Closer }` эквивалентно перечислению всех методов.
- Интерфейсы являются ссылочными типами, но сами по себе **не аллоцируют память** под данные.


## Популярные интерфейсы в стандартной библиотеке
| Интерфейс         | Методы                               | Назначение                                                 |
| ----------------- | ------------------------------------ | ---------------------------------------------------------- |
| `fmt.Stringer`    | `String() string`                    | Форматирование через `fmt.Println`, `fmt.Sprintf("%v", v)` |
| `error`           | `Error() string`                     | Стандартный механизм обработки ошибок                      |
| `io.Reader`       | `Read([]byte) (int, error)`          | Чтение потоков данных                                      |
| `io.Writer`       | `Write([]byte) (int, error)`         | Запись потоков данных                                      |
| `context.Context` | `Deadline(), Done(), Err(), Value()` | Отмена операций, таймауты, передача request-scoped данных  |
| `sort.Interface`  | `Len(), Less(), Swap()`              | Сортировка пользовательских коллекций                      |


## Приведение типов: `Type Assertion` и `Type Switch`

### Type Assertion (проверка типа)
```go
var i interface{} = "hello"

s := i.(string)        // ⚠️ Паника, если тип не совпадает
s, ok := i.(string)    // ✅ Безопасно: ok == true/false
```


### Type Switch (выбор по типу)
```go
**func process(v any) {
    switch val := v.(type) {
    case int:
        fmt.Println("int:", val)
    case string:
        fmt.Println("string:", val)
    case nil:
        fmt.Println("nil value")
    default:
        fmt.Printf("unknown: %T\n", val)
    }
}**
```

> `type switch` компилятором преобразуется в серию быстрых проверок `itab->_type`, работает за `O(1)`.


## Внутреннее устройство интерфейсов

Интерфейс в Go — это не просто указатель. Это структура из двух полей: `(тип, значение)`.
В рантайме (`runtime/runtime2.go`) существуют две структуры: eface, iface 


### `eface` (empty interface / `any`)
```go
type eface struct {
    _type *_type          // указатель на описание типа
    data  unsafe.Pointer  // указатель на данные
}
```

### `iface` (non-empty interface)
```go
type iface struct {
    tab  *itab            // таблица методов
    data unsafe.Pointer   // указатель на данные
}

type itab struct {
    inter *interfacetype  // описание интерфейса
    _type *_type          // конкретный тип
    hash  uint32
    fun   [1]uintptr      // массив указателей на методы (диспетчеризация)
}
```

### Как это работает на практике?

1. При присваивании `var r io.Reader = &bytes.Buffer{}`:
    - `tab` указывает на `itab`, где `_type` = `*bytes.Buffer`, `inter` = `io.Reader`.
    - `fun[0]` хранит указатель на метод `Read` для `*bytes.Buffer`.
2. Вызов `r.Read()` → рантайм читает `tab.fun[0]` и вызывает функцию напрямую. **Динамическая диспетчеризация O(1)**.
3. Если значение маленькое (до 8 байт на amd64), оно может храниться прямо в `data` без аллокации (inlining/escapes).

> **Производительность:** Вызов метода через интерфейс чуть медленнее прямого вызова (индирекция + загрузка `itab`), но разница обычно <5%. Главная цена — аллокация при "упаковке" (boxing) значений в интерфейс.


## Пустые интерфейсы (`any`) vs `nil`-интерфейсы

### Пустые интрефейсы`any` (`interface{}`)

- Может хранить значение любого типа.
- Внутренне: `(_type, data)`.
- Используется, когда тип заранее неизвестен или обобщённый (десериализация JSON, generic-контейнеры до 1.18 и т.д.).


### `nil`-интерфейс vs интерфейс с `nil` значением
```go
**var buf *bytes.Buffer = nil
var r io.Reader = buf

fmt.Println(r == nil) // ⚠️ false! 
// Потому что r = (type: *bytes.Buffer, data: nil)
// Интерфейс nil только когда type == nil И data == nil**


var r2 io.Reader
fmt.Println(r2 == nil) // true (type=nil, data=nil)
```

> **Правило:** Интерфейс равен `nil` **только** когда и тип, и значение `nil`.

> **Как избежать:** Не присваивайте конкретные `nil`-указатели интерфейсам. Возвращайте `nil` напрямую или используйте конкретные типы в сигнатурах, если `nil` семантически важен.



## Лучшие практики использования интерфейсов

- **Принимайте интерфейсы, возвращайте структуры**  
    `func Process(r io.Reader) error` → хорошая. `func GetData() io.Reader` → плохая (скрывает реальную реализацию).
- **Держите интерфейсы маленькими**  
    1-2 метода. Легче реализовать, легче тестировать, меньше coupling. (`io.Reader`, `error`, `fmt.Stringer`).
- **Определяйте интерфейсы там, где они используются**  
    Не создавайте `interfaces.go` в корне пакета. Клиент кода должен диктовать контракт.
- **Используйте дженерики для типовых контейнеров**  
    С Go 1.18 предпочтительнее `[]T` или `map[K]V`, чем `[]any` + `type switch`, если известна общая семантика.

## Антипаттерны
| Антипаттерн                              | Почему плохо                                  | Как исправить                                       |
| ---------------------------------------- | --------------------------------------------- | --------------------------------------------------- |
| **Interface Pollution**                  | Пакет экспортирует интерфейсы "на будущее"    | Удаляйте до тех пор, пока не появится 2+ реализации |
| **Возврат интерфейсов из функций**       | Скрывает тип, усложняет отладку и оптимизацию | Возвращайте конкретные типы                         |
| `any` вместо дженериков/конкретных типов | Потеря типобезопасности, runtime-проверки     | Используйте `constraints` или дженерики             |
| Большой интерфейс (10+ методов)          | Трудно мокировать, сложно расширять           | Разбейте на мелкие (Interface Segregation)          |
