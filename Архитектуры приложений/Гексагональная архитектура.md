
## Суть

Сама по себе гексагональная архитектура является частной имплементацией чистой архитектуры.
Цель гексагональной  архитектуры такая же как и чистой - **полная изоляции бизнес-логики (ядра/домена) от внешних воздействий/деталей** (баз данных, UI, сторонних API, очередей сообщений, фреймворков).

Приложение представляется как «ядро», окруженное слоями портов и адаптеров.

- Ядро не знает, кто к нему обращается и где хранятся данные. Оно лишь предоставляет набор операций (портов) и ожидает, что внешние системы будут общаться с ним на его собственном языке (на языке доменных сущностей).
- Вся магия подключения к реальному миру (базе данных, HTTP) происходит на границах системы с помощью адаптеров.

**Главная цель:** сделать бизнес-логику независимой от инфраструктуры, что позволяет легко менять базы данных, протоколы передачи данных или UI, не переписывая ядро, а также писать юнит-тесты без поднятия тяжелых зависимостей.

## Ключевые понятия архитектуры

- **Domain / Core (Домен / Ядро):** Бизнес-сущности, модели, инварианты и правила. Самая защищенная часть приложения.
- **Application / Use Cases (Приложение / Сценарии использования):** Оркестрация бизнес-логики. Сценарии, которые описывают, _что_ может делать приложение (например, «Зарегистрировать пользователя»).
- **Port (Порт):** Контракт (как тип это интерфейс), определяющий, как ядро общается с внешним миром или как внешний мир общается с ядром.
- **Adapter (Адаптер):** Конкретная реализация порта. Переводит вызовы из внешнего формата (например, HTTP-запрос или SQL-запрос) во внутренний формат домена и обратно.
- **Driving Adapter / Primary Port (Входящий):** Внешние акторы, которые **инициируют** вызовы к нашему приложению (например, HTTP-контроллеры, CLI-команды, gRPC-сервер, сообщения из Kafka).
- **Driven Adapter / Secondary Port (Исходящий):** Внешние системы, к которым _наше приложение обращается_ за данными или действиями (например, репозитории в БД, клиенты внешних API, SMTP-сервер для отправки писем).
- **Dependency Inversion (Инверсия зависимостей):** Фундаментальный принцип. Зависимости направлены _внутрь_ (к домену). Инфраструктура зависит от домена, а не наоборот.


## Использование интерфейсов (портов)

### Driven-side (Исходящие / База данных, API)
Здесь все понятно. Ядро определяет интерфейс `UserRepository`, а адаптер (PostgreSQL, MongoDB) его реализует. Это позволяет подменить БД на in-memory для тестов или сменить СУБД без изменения кода ядра.
> В golang-приложениях исходящие порты объявляются в слое приложения или слое домена

### Driving-side (Входящие / HTTP, gRPC)

Причинами использования интерфейсов/портов на данном уровне портов может быть:
- **Необходимость отвязка внутреннего слоя от транспорта:** Ядро (Use Case) не должно знать, что оно вызвано через HTTP. Если завтра вы захотите добавить gRPC или CLI, ядро не должно измениться. 
- **Облегчение тестирования:** Если ядро зависит от интерфейса, мы можем протестировать сценарий использования (Use Case), просто вызвав его метод напрямую, без необходимости поднимать HTTP-сервер, роутеры и сериализаторы.
- **Изоляция зависимостей:** Если бы ядро напрямую принимало `http.Request`, оно бы «загрязнялось» деталями фреймворка `net/http`.

Часто в Go-приложениях мы не создаем входящих портов если он используется только одним HTTP-обработчиком. Мы просто создаем структуру `UserService` в `internal/app`, и HTTP-адаптер принимает её (или интерфейс, определенный _внутри пакета HTTP-адаптера_, если мы хотим моковать Use Case в тестах хендлера). 
_Почему:_ Go не требует интерфейсов для всего. Если Use Case — это просто структура с методами, HTTP-адаптер может зависеть от неё напрямую (принимая указатель `*UserService`). 

### Где объявлять driving-side интерфейсы/порты?

####  **Интерфейс в пакете адаптера (driving-side)**
 Это классическая Go-идиома: _«интерфейс определяется там, где используется»_.
 ```go
 // internal/adapter/driving/http/handler.go
package http

type UserRegistrar interface {
    RegisterUser(ctx context.Context, email string) error
}

type Handler struct {
    registrar UserRegistrar
}
 ```

**Плюсы:**

- Полное соответствие Go-идиомам.
- Каждый адаптер сам решает, какой контракт ему нужен (принцип Interface Segregation).
- HTTP-адаптер может требовать `RegisterUser`, а gRPC-адаптер — `RegisterUserWithMetadata`. У каждого свой интерфейс.

**Минусы:**

- Если есть несколько адаптеров, использующих один и тот же Use Case, придётся дублировать интерфейс или выносить его в общее место.
- Ядро (`app`) не «видит» своего собственного контракта со стороны потребителя.

#### Интерфейс в пакете приложения (`app`)
Интерфейс объявляется рядом с реализацией Use Case.
```go
// internal/app/user_service.go
package app

// UserServiceContract — контракт, который приложение 
// предоставляет внешнему миру.
type UserServiceContract interface {
    RegisterUser(ctx context.Context, email string) error
    GetUser(ctx context.Context, id string) (*domain.User, error)
}

type UserService struct {
    repo  domain.UserRepository
    email domain.EmailSender
}

func (s *UserService) RegisterUser(ctx context.Context, email string) error { ... }
func (s *UserService) GetUser(ctx context.Context, id string) (*domain.User, error) { ... }
```

**Плюсы:**

- Контракт приложения задокументирован в одном месте.
- Удобно, когда несколько адаптеров (HTTP, gRPC, CLI) используют один и тот же Use Case.
- Легко моковать в тестах адаптеров.

**Минусы:**

- Нарушает Go-идиому «интерфейс у потребителя».
- Интерфейс может разрастись и содержать методы, ненужные конкретному адаптеру (нарушение ISP).
- Адаптеры начинают зависеть от пакета `app`, хотя должны зависеть только от контракта.

**Когда использовать:** несколько адаптеров используют один Use Case и им нужен общий контракт.


#### Отдельный пакет `ports` (каноническая гексагональная архитектура)
Интерфейсы выносятся в специальный пакет, который находится «на границе».
```
internal/
  domain/           # сущности + driven-порты
  ports/            # ← отдельный пакет для входящих портов
    user_ports.go
  app/              # реализация Use Cases
  adapter/
    driving/        # HTTP, gRPC
    driven/         # Postgres, SMTP
```

```go
// internal/ports/user_ports.go
package ports

type UserRegistrar interface {
    RegisterUser(ctx context.Context, email string) error
}

type UserReader interface {
    GetUser(ctx context.Context, id string) (*domain.User, error)
}
```

```go
// internal/app/user_service.go
package app

import "myapp/internal/ports"

// UserService реализует ports.UserRegistrar и ports.UserReader
type UserService struct { ... }
```

```go
// internal/adapter/driving/http/handler.go
package http

import "myapp/internal/ports"

type Handler struct {
    registrar ports.UserRegistrar
}
```

**Плюсы:**

- Максимально близко к канону Кокберна.
- Чистое разделение: `domain` — ядро, `ports` — контракты, `app` — реализация, `adapter` — инфраструктура.
- Адаптеры не зависят от `app`, только от `ports`.
- Легко добавлять новые адаптеры.

**Минусы:**

- Лишний пакет и уровень абстракции — для маленьких проектов это over-engineering.
- Go-сообщество часто считает это избыточным.
- Интерфейсы в `ports` могут не совпадать с реальными потребностями адаптеров (снова риск нарушения ISP).

**Когда использовать:** крупный проект с множеством адаптеров, команда хочет строго следовать гексагональной архитектуре, есть готовность платить за чистоту.


#### Практическая рекомендация

Для большинства Go-приложений я бы советовал **гибридный подход**:
1. **Если адаптер один** (например, только HTTP) — объявляйте интерфейс **в пакете адаптера**. Это идиоматично и просто.
2. **Если адаптеров несколько** и они используют один Use Case — объявляйте интерфейс **в пакете `app`** рядом с реализацией. Это разумный компромисс.
3. **К пакету `ports`** прибегайте только в крупных проектах, где строгое разделение слоёв важнее лаконичности.


### Базовый пример структуры гексагонального приложения

```
cmd/
 └─ main.go               # Точка входа, сборка (DI)
internal/
  └─ domain/               # Ядро: сущности и исходящие порты 
	  └─ user.go
  └─ app/                  # Сценарии использования (Use Cases)
	  └─ user_service.go
  └─ adapter/
	  └─ driven/             # Исходящие адаптеры (реализации портов)
	      └─ memory_repo.go
		  └─ mock_email.go
	  └─ driving/            # Входящие адаптеры (транспорт)
		  └─ http_handler.go
```

- **Домен (`domain`)** не импортирует ничего, кроме стандартной библиотеки. Он задает правила.
- **Порты (интерфейсы)** для БД и внешних API объявляются **в домене**.
- **Use Cases (`app`)** принимают интерфейсы из домена. Они не знают про `net/http`.
- **Адаптеры (`adapter`)** импортируют домен и приложение. Они реализуют интерфейсы домена (для `driven`) и вызывают методы приложения (для `driving`).
- **Сборка (`main`)** знает обо всем и связывает всё воедино. Если завтра вы захотите заменить `InMemoryUserRepo` на `PostgresUserRepo`, вам нужно будет изменить код **только** в `cmd/main.go`. Ядро и HTTP-обработчики останутся нетронутыми.
