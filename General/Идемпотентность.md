
### Общие сведения

Идемпотентность – на уровне приложения, это гарантия, что повторный запрос даёт тот же результат, что и первый. 
Использование идемпотентности -  это требование для любой системы, где есть сеть. 
Запросы дублируются всегда: ретраи клиента, таймауты, балансировщики, 
очереди сообщений

> Нажал "Оплатить" пять раз – списание одно

Предпосылки применения идемпотентности
- В распределённых системах запросы теряются, дублируются, ретраятся
- Клиент не знает, дошёл запрос или нет, и отправляет снова
- Сеть ненадёжна
- Если сервер не идемпотентен — данные ломаются

Идемпотентные операции:
- **GET** - читаем данные, ничего не меняем.  Хоть 100 раз вызови, результат один
- **PUT** - заменяет ресурс целиком PUT /users/66 {name: "Alex"} — сколько ни вызови, 
результат один и тот же
- **DELETE** - удаляет ресурс:
	- Если удаление проводится по ключу - первый вызов удалит ресурс по ключу, повторные вернут **404**. Состояние системы не меняется.


Не идемпотентные операции
- **POST** - НЕ идемпотентен. Каждый вызов создаёт новый ресурс или выполняет новое действие 
Именно POST требует дополнительной защиты

Операции, идемпотентность которых зависит от реализации 
- **PATCH** - частичное изменение ресурса: 
	- balance += 100 — не идемпотентен.
	- balance = 500 — идемпотентен
	- частичное удаление из данных из ресурса также может быть не идемпотентным

### Idempotency Key

Способ реализации ключа идемпотентности - генерация клиентом уникального ключа (UUID). Далее клиент  отправляет его с каждым запросом в заголовке `Idempotency-Key`

Как это работает?
- Сервер проверяет: есть ли тот ключ в хранилище
	- Нет - выполняет операцию, сохраняет ключ и результат
	- Есть - возвращает сохранённый результат без повторного выполнения
```go
func (h *Handler) CreatePayment(w http.ResponseWriter, r *http.Request) {
    key := r.Header.Get("Idempotency-Key")

    // Уже выполняли?
    if result, ok := h.cache.Get(key); ok {
        json.NewEncoder(w).Encode(result)
        return
    }

    result := h.service.Pay(r.Context(), req)
    h.cache.Set(key, result, 24*time.Hour)
    json.NewEncoder(w).Encode(result)
}
```

### Способы обеспечения идемпотентности
- Уникальный  constraint в БД:
> UNIQUE(order_id, operation)
база не даст создать дубль. Дёшево и 
надёжно для простых случаев


- INSERT ... ON CONFLICT  DO NOTHING:
PostgreSQL выполнит вставку только если нет конфликта. Атомарно, без гонок
```go
// PostgreSQL: INSERT с защитой от дубля
_, err := db.ExecContext(ctx, `
    INSERT INTO payments (idempotency_key, amount, status)
    VALUES ($1, $2, 'success')
    ON CONFLICT (idempotency_key) DO NOTHING
`, key, amount)
```
- Conditional update (оптимистичная блокировка):
>UPDATE ... WHERE version = 5
обновление пройдёт только если версия совпадает. Повторный запрос с той же версией ничего  
не изменит

- Естественный идемпотентный дизайн:
> Вместо balance += 100
используй balance = 500
Вместо "создай заказ" используй 
"создай заказ с ID=uuid". 
Проектируй операции так, чтобы 
повтор был безопасен


#### Хранилище ключей: 
Обычно это Redis с TTL (обычно 24-72 часа) или отдельная таблица в БД. Ключ должен жить 
достаточно долго, чтобы покрыть все ретраи.



### РЕЗЮМЕ
- GET, PUT, DELETE идемпотентны  по природе. POST — нет
- Idempotency Key (UUID  от клиента) — стандартный способ защиты POST-запросов
- Храни ключи в Redis с TTL или  в отдельной таблице
- ON CONFLICT DO NOTHING — простая защита на уровне БД
- Проектируй операции идемпотентными с самого начала: 
	- абсолютные значения вместо дельт, 
	- клиентские ID вместо серверных
