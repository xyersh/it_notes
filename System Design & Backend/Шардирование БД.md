




Шардирование - разделение одной БД на несколько отдельных БД
- Данные в отдельных  шардах БД будут разные, в зависимости от выбранного способа шардирования
- Шардирование происходит в разрезе отдельных таблиц а не всей БД. Некоторые таблицы в БД могут вообще не шардироваться
- шардирование масштабирует запись и изменение (хорошо если нагрузка на запись большая)




### Горизонтальное шардирование

- разделение строк таблицы по разным БД 
- используется **ключ шардирования**, как правило это первичный ключ, 
- в какой шард запись попадет - определяется по значению ключа шардирования на основании установленных правил (например записи с четными id - в один шард, записи с нечетным - в другой). Распределение по шардам происходит подобно распределению данных по бакетам в мапе.
- В реале для распределения по шардам используется хэш-функция.


#### ВЫБОР КЛЮЧА ШАРДИРОВАНИЯ

Плохой ключ шардирования приводит к неравномерному распределению данных, горячим точкам, где один шард перегружен, а другие простаивают, и запросам, которые должны обращаться ко всем шардам, чтобы найти результат. Хороший ключ шардирования равномерно распределяет данные, соответствует вашим паттернам запросов и масштабируется по мере роста системы.
Вот что делает ключ шардирования хорошим:

**Высокая кардинальность (cardinality, мощность множества)**: ключ должен иметь много уникальных значений. Шардирование по булевому полю (true/false) означает, что у вас может быть максимум два шарда, что сводит на нет его целесообразность. Шардирование по `user_id` при миллионах пользователей дает достаточно пространства для распределения данных.

**Равномерное распределение**: значения должны равномерно распределяться по шардам. Если мы шардируем по стране и 90% ваших пользователей в России, этот шард будет значительно больше остальных. `user_id` обычно распределяется хорошо. Временные метки (timestamps) создания могут подойти, если новые записи не все попадают на самый последний шард.

**Соответствие запросам**: ваши самые частые запросы в идеале должны обращаться только к одному шарду. Если  шардировать пользователей по `user_id`, запросы вроде "получить профиль пользователя" или "получить заказы пользователя" обращаются к одному шарду. Запросы, охватывающие все шарды, становятся дорогими.

##### Примеры хороших ключей шардирования:

- **user_id** для пользователь-центричного приложения: высокая кардинальность (миллионы пользователей), равномерное распределение, и большинство запросов ограничены одним пользователем ("покажи мне данные этого пользователя").

- **order_id** для таблицы заказов в интернет-магазине: высокая кардинальность (миллионы заказов), запросы обычно ограничены конкретным заказом ("получить детали заказа", "обновить статус заказа"), и заказы равномерно распределяются во времени.

##### Примеры плохих ключей шардирования:
- **is_premium** (булево поле): только два возможных значения означают максимум два шарда. Один шард получает всех премиум-пользователей, другой - всех обычных. Если большинство пользователей обычные, этот шард перегружен.

- **created_at** для растущей таблицы: все новые записи попадают на самый последний шард. Этот шард становится горячей точкой для записи, в то время как старые шарды не обрабатывают почти никакого трафика.


#### СТРАТЕГИИ ШАРДИРОВАНИЯ

##### Range Based - Шардирование по диапазонам
```
Шард 1 -> User IDs 1–1M
Шард 2 -> User IDs 1M–2M
Шард 3 -> User IDs 2M–3M
```
Главное преимущество шардирования по диапазонам - простота и поддержка эффективных сканирований по диапазонам. Если вам нужны все заказы между `user_id` 500K и 600K, вы обращаетесь только к одному шарду.

##### Key Based - Хеш-шардирование (по умолчанию)
Хеш-шардирование использует хеш-функцию для равномерного распределения записей по шардам. Вместо назначения диапазонов мы:
- берем ключ шардирования, например `user_id`, 
- хешируем его, 
- берем полученный хэш и получаем остаток его деления на количество шардов
- полученное число  используем как  результат для выбора шарда.

Например, если у нас 4 шарда, мы можем маршрутизировать пользователей так:
```
shard = hash(user_id) % 4

Пользователь 42  -> hash(42) % 4 = Шард 2
Пользователь 99  -> hash(99) % 4 = Шард 3
Пользователь 123 -> hash(123) % 4 = Шард 1

```
Большое преимущество хеш-шардирования - равномерное распределение. Поскольку хеш-функция перемешивает входные значения, новые пользователи распределяются равномерно по всем шардам.
Недостаток проявляется, когда нужно добавлять или удалять шарды. Если вы переходите с 4 шардов на 5, операция деления по модулю меняется с `% 4` на `% 5`, что означает, что почти каждая запись будет отображаться на другой шард. Вам придется перемещать огромные объемы данных.
Здесь на помощь приходит согласованное хеширование. Согласованное хеширование минимизирует перемещение данных при добавлении или удалении шардов.

##### Directory Based - Шардирование на основе каталога
Шардирование на основе каталога (directory-based sharding) используется специальная таблица поиска, чтобы определить, где хранится каждая запись. Вместо использования формулы хранятся  соответствия между записями и шардами в таблице или сервисе отображения. 

 | user             | shard  |
 | ---------------- | ------ |
 | Пользователь 15  | Шард 1 |
 | Пользователь 87  | Шард 3 |
 | Пользователь 204 | Шард 2 |

Мощь шардирования на основе каталога - в гибкости. Если конкретный пользователь генерирует огромный трафик, его можно перенести  на выделенный шард. Если нужно перебалансировать нагрузку - просто обновляем таблицу отображения. Для данной политики шардирования можно реализовать сложную логику шардирования, невозможную с простой хеш-функцией.

Недостаток в том, что каждый запрос требует обращения к каталогу (сервису, или таблице сопоставления). Прежде чем запросить данные пользователя, необходимо спросить у сервиса-каталога, на каком шарде находится этот пользователь. Это добавляет задержку к каждому запросу и делает сервис-каталог критической зависимостью. Если каталог откажет, вся  система перестанет работать, даже если все шарды с данными функционируют.

Шардирование на основе каталога имеет смысл, когда необходима максимальная гибкость и мы можем позволить себе дополнительные обращения к каталогу. Большинство систем начинают с хеш-шардирования или шардирования по диапазонам и используют каталог только при наличии специфических требований.

#### РОУТИНГ

##### На стороне клиента
- это когда клиент сам знает, к какому шарду стучаться.
**Плюсы:**
- нет лишних узлов 
**Минусы:**
- дополнительная логика на клиенте
- сложности в обновлении хостов. Для обеспечения валидного роутинга по шардам клиент всегда должен обладать актуальной информацией  об имеющихся шардах.

##### PROXY
- когда между клиентом и шардированной БД находится прокся, которая собственно роутит на нужный шард
**Плюсы:**
- приложение не знает о шардировании. Вся логика распределения запросов возлагается на проксю.
**Минусы:**
- дополнительный сетевой узел (latency)
- потеря функциональности. Прокся не умеет мёрджить и группировать данные из разных шардов.
- единая точка отказа.

##### COORDINATOR
- когда между клиентом и шардированной БД находится координатор (умная прокся), которая отвечает за роутит на нужный шард. Для некоторых типов БД имеются готовые координаторы.
**Плюсы:**
- кэширование 
- можно джойнить и группировать данные из разных шардов.
- приложение не знает о шардировании
**Минусы:**
- дополнительный сетевой узел (latency)
- инфраструктурная сложность
- единая точка отказа.
- нагрузка


#### ПЕРЕБАЛАНСИРОВКА
Это перенос данных из одного шарда в другой. (старый шард выходит из строя, перенос из одного дата-центра в другой). Данный термин применим для случая когда итоговое количество шардов не меняется, а лишь часть данных переезжает из одного шарда на другой. 

В момент перебалансировки данных возможны следующие политики для работы с операциями IO
- только чтение
-  запись на target, чтение из target и source. Старые запись в source остаются
- Логическая репликация с source на target. После синхронизации переключаемся на target
- смешанный подход

#### Проблемы горизонтального шардирования


- нужно правильно выбирать ключ шардирования
	- данные должна распределяться по шардам равномерно
	- избегать мульташардовых запросов. В противном случае растет задержка в выполнении запросов.
- Решардинг - процесс добавления дополнительных шаров. Если соломку предварительно не подстелить, то придется для каждой записи пересчитать хэш и номер нового шарда в который попадет запись. Если номер нового шарда не соответствует старому - придется переносить записи (по факту - много записей). Данная проблема решается использованием виртуальных бакетов.

> **Виртуальные бакеты(шарды)** -  когда таблицу в одной БД заранее разбиваем на виртуальные бакеты. и данные равномерно распределяются по вирт. бакетам (допустим из будет 8 штук). 
Далее когда таблица становиться очень большой (условно) половишу вирт. бакетов (4 из 8ми) переном в другую БД. Перехэшировать записи при этом не потребуется.

- нет транзакций и блокировок нет изоляции транзакций. Приходится реализовывать распределенные транзакции - а это больно.
- сложно делать джойны в таких шардах ( открыт  вопрос производительности исполнения таких запросов)


### Вертикальное шардирование

Вертикальное шардирование - это разделения таблицы по столбцам - разные столбцы таблицы уходят в разные шарды.
Например: есть таблица со столбцами:
```
- id
- created_at
- name
- description
- specification
- images
- videos
```

при вертикальном шардировании:
- id, created_at, name- оставляем в одной таблице
- id, description, specification - переносим в другой шард
- id, images, videos - переносим в третий шард
при этом id будет содержаться во всех 3х шардах для связывания соответствующих записей


Можно совмещать вертикальное и горизонтальное шардирования таблицы
