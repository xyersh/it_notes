
Оптимистичные и пессимистичные блокировки — это две фундаментальные стратегии управления конкурентным доступом к данным (Concurrency Control).

Главное отличие, которое нужно понять сразу: **Пессимистичная блокировка — это механизм самого движка БД**, а **Оптимистичная блокировка — это архитектурный паттерн**, который реализуется на уровне SQL-логики и приложения (в PostgreSQL нет специальной команды `OPTIMISTIC LOCK`).

Ниже подробно разобраны обе стратегии, их реализация в PostgreSQL и поведение.

### 1. Пессимистичная блокировка (Pessimistic Locking)

**Философия:** «Пессимист ожидает проблем». Мы предполагаем, что конфликт записи произойдет с высокой вероятностью, поэтому **сначала блокируем данные**, а потом читаем и изменяем их.

#### Как реализуется в PostgreSQL

Реализуется через явные механизмы блокировок движка (о которых мы говорили в прошлом ответе):

- На уровне строк: `SELECT ... FOR UPDATE` или `FOR SHARE`.
- На уровне таблиц: `LOCK TABLE ...`.

#### Как выражается работа (Поведение)

1. **Транзакция А** читает строку с `FOR UPDATE`. Движок PostgreSQL ставит на эту строку блокировку `FOR UPDATE`.
2. **Транзакция Б** пытается прочитать эту же строку с `FOR UPDATE` (или изменить её).
3. **Поведение:** Транзакция Б **не получает ошибку**, а **зависает (ждет)**. Она стоит в очереди до тех пор, пока Транзакция А не выполнит `COMMIT` или `ROLLBACK`.
4. Если А сделала `COMMIT`, Б получает актуальные данные, блокирует их и продолжает работу.

#### Пример из жизни: Бронирование места в кино

Два пользователя одновременно выбирают одно и то же место.

```sql
-- Пользователь 1 (Транзакция А)
BEGIN;
SELECT seat_id FROM cinema_seats WHERE movie_id = 10 AND seat_number = 'A5' FOR UPDATE;
-- БД вернула seat_id и заблокировала строку.
-- Пользователь 1 идет на страницу оплаты (это занимает 2 минуты).

-- Пользователь 2 (Транзакция Б) в это же время
BEGIN;
SELECT seat_id FROM cinema_seats WHERE movie_id = 10 AND seat_number = 'A5' FOR UPDATE;
-- ПОВЕДЕНИЕ: Запрос Транзакции Б "завис". Он ждет, пока Транзакция А не закончит.
```


_Минус:_ Если пользователь 1 ушел пить кофе и не завершил транзакцию, пользователь 2 будет ждать вечно (или пока не сработает `statement_timeout` / `lock_timeout`).


### 2. Оптимистичная блокировка (Optimistic Locking)

**Философия:** «Оптимист верит в лучшее». Мы предполагаем, что конфликты случаются редко. Мы **не блокируем данные при чтении**, а проверяем, не изменил ли их кто-то другой, непосредственно в момент сохранения.

#### Как реализуется в PostgreSQL

В самом PostgreSQL нет встроенной команды для оптимистичных блокировок. Они реализуются через **версионирование строк** (или сравнение хешей/временных меток). В таблицу добавляется служебное поле, например, `version` (integer) или `updated_at` (timestamp).

#### Как выражается работа (Поведение)

1. **Транзакция А** читает строку (без всяких `FOR UPDATE`). Запоминает её `version = 1`.
2. **Транзакция Б** читает эту же строку. Тоже видит `version = 1`.
3. **Транзакция А** обновляет строку. В `UPDATE` она указывает `version = version + 1`. Строка успешно обновлена, `version` стал `2`.
4. **Транзакция Б** пытается обновить строку, но в `WHERE` указывает свой старый `version = 1`.
5. **Поведение:** Условие `WHERE version = 1` не совпадает с актуальным `2`. Команда `UPDATE` срабатывает, но **затрагивает 0 строк**. Приложение видит, что обновлено 0 строк, и понимает, что произошел конфликт. Транзакция Б откатывается (`ROLLBACK`), а пользователю выдается ошибка: _"Данные были изменены другим пользователем, обновите страницу"_.

#### Пример из жизни: Редактирование статьи в CMS

Два редактора открыли одну статью. Оба нажали "Редактировать".

```sql
-- 1. Структура таблицы
CREATE TABLE articles (
    id INT PRIMARY KEY,
    title TEXT,
    body TEXT,
    version INT NOT NULL DEFAULT 1 -- Поле для оптимистичной блокировки
);

INSERT INTO articles (id, title, body, version) VALUES (1, 'Старый заголовок', 'Текст', 1);
```

```sql
-- Редактор 1 (Транзакция А)
BEGIN;
-- Читает без блокировок
SELECT id, title, body, version FROM articles WHERE id = 1; 
-- Получает: version = 1. Редактор 1 долго печатает новый текст.

-- Редактор 2 (Транзакция Б)
BEGIN;
SELECT id, title, body, version FROM articles WHERE id = 1;
-- Получает: version = 1. Редактор 2 быстро исправляет опечатку и сохраняет.

-- Сохранение Редактора 2 (Транзакция Б)
UPDATE articles 
SET title = 'Исправленный заголовок', body = 'Текст с опечаткой', version = 2 
WHERE id = 1 AND version = 1; -- Условие оптимистичной блокировки
COMMIT; -- Успешно обновлена 1 строка. version теперь равен 2.

-- Сохранение Редактора 1 (Транзакция А) - происходит позже
-- В приложении (или в PL/pgSQL) мы проверяем, сколько строк затронул UPDATE:
DO $$
DECLARE
    rows_updated INTEGER;
BEGIN
    UPDATE articles 
    SET title = 'Новый заголовок от Р1', body = 'Новый текст', version = 2 
    WHERE id = 1 AND version = 1; -- ОШИБКА! В БД version уже равен 2.
    
    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    
    IF rows_updated = 0 THEN
        RAISE EXCEPTION 'Оптимистичная блокировка: Статья была изменена другим редактором!';
        -- Приложение поймает эту ошибку и покажет юзеру "Конфликт версий".
    END IF;
END $$;
```


### Сравнительная таблица: Когда что использовать


|Характеристика|Пессимистичная блокировка|Оптимистичная блокировка|
|---|---|---|
|**Механизм**|Встроенный механизм БД (`FOR UPDATE`).|Архитектурный паттерн (доп. колонка `version` + логика в `UPDATE`).|
|**Поведение при конфликте**|Транзакция **ждет** (блокируется).|Транзакция **падает** (ошибка / откат).|
|**Нагрузка на БД**|Выше. Удержание блокировок тратит ресурсы, возможны `deadlocks` (взаимные блокировки).|Ниже. Нет удержания блокировок, но требуются повторные попытки (retries) при ошибках.|
|**Риск Deadlock**|**Высокий** (если блокировать ресурсы в разном порядке).|**Отсутствует** (так как нет явных блокировок).|
|**Идеальный сценарий**|Высокая конкуренция за одни и те же данные (финансы, списание баланса, бронирование 1 билета).|Низкая конкуренция, долгие транзакции (редактирование профилей, форм, документов).|
|**Длительность транзакции**|Должна быть **короткой** (иначе другие будут долго ждать).|Может быть **долгой** (пользователь может думать над формой час).|

### Резюме 

- Используем **пессимистичную** (`SELECT ... FOR UPDATE`), если цена ошибки или двойного списания критична, а транзакция выполняется быстро (миллисекунды).
- Используем **оптимистичную** (колонка `version`), если транзакция включает "человеческий фактор" (пользователь заполняет форму, читает текст) или если вы хотите избежать взаимных блокировок (deadlocks) в сложной бизнес-логике. В современных ORM (Hibernate, Entity Framework, Django) оптимистичная блокировка часто включается одной аннотацией (например, `@Version`), которая под капотом генерирует описанный выше SQL.
