
В PostgreSQL система управления блокировками базируется на модели MVCC (Multi-Version Concurrency Control). Чтобы избежать путаницы, важно разделять два понятия: **уровни изоляции транзакций** (Read Committed, Repeatable Read, Serializable) и **режимы (уровни) самих блокировок** (Table-level и Row-level).

### Блокировки на уровне таблиц (Table-level Locks)

В PostgreSQL существует 8 режимов блокировок на уровне таблиц. Они нужны в основном для защиты структуры таблицы (DDL) и метаданных, а также для координации DML-операций.

|Режим блокировки|Когда применяется автоматически (неявно)|Когда применяется явно|
|---|---|---|
|**ACCESS SHARE**|Обычный `SELECT`.|Редко.|
|**ROW SHARE**|`SELECT ... FOR UPDATE` / `FOR SHARE`.|`LOCK TABLE ... IN ROW SHARE MODE`.|
|**ROW EXCLUSIVE**|`INSERT`, `UPDATE`, `DELETE`.|`LOCK TABLE ... IN ROW EXCLUSIVE MODE`.|
|**SHARE UPDATE EXCLUSIVE**|`VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY`.|Защита от одновременного изменения схемы и вакуумирования.|
|**SHARE**|`CREATE INDEX` (без `CONCURRENTLY`).|Защита таблицы от изменений при чтении.|
|**SHARE ROW EXCLUSIVE**|Не используется автоматически.|Редкие случаи сложной синхронизации.|
|**EXCLUSIVE**|Не используется автоматически.|Редкие случаи сложной синхронизации.|
|**ACCESS EXCLUSIVE**|`ALTER TABLE`, `DROP TABLE`, `TRUNCATE`, `REINDEX`, `VACUUM FULL`, `REFRESH MATERIALIZED VIEW` (без CONCURRENTLY).|`LOCK TABLE ... IN ACCESS EXCLUSIVE MODE`.|

#### Поведение (Матрица совместимости)

Поведение блокировок выражается в том, какие из них могут сосуществовать (не конфликтовать), а какие будут ждать снятия друг друга. _Правило «чтения и записи» в PG:_ **Чтения не блокируют чтения, чтения не блокируют записи, записи блокируют записи (на уровне строк) и структуру (на уровне таблиц).**

- **ACCESS SHARE** конфликтует только с `ACCESS EXCLUSIVE`. (Таблица читается, но её нельзя удалить/изменить структуру).
- **ROW EXCLUSIVE** (стандартный для `UPDATE/INSERT`) конфликтует с `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE`. (Можно параллельно писать в разные строки, но нельзя менять структуру таблицы).
- **ACCESS EXCLUSIVE** — самый строгий. Конфликтует со **всеми** режимами. Полностью блокирует таблицу.


### Блокировки на уровне строк (Row-level Locks)

Используются для защиты конкретных строк от одновременного изменения. В PostgreSQL нет явного синтаксиса для их вызова вне `SELECT`, они применяются автоматически при `UPDATE/DELETE` или явно через `SELECT ... FOR ...`.

|Режим|Когда применяется|Поведение (что блокирует)|
|---|---|---|
|**FOR KEY SHARE**|Автоматически при проверке внешних ключей (Foreign Keys).|Самая слабая. Блокирует только изменение или удаление первичного/уникального ключа этой строки.|
|**FOR SHARE**|`SELECT ... FOR SHARE`.|Блокирует строку от изменения или удаления другими транзакциями. Другие транзакции могут брать `FOR SHARE` или `FOR KEY SHARE`.|
|**FOR NO KEY UPDATE**|Автоматически при `UPDATE`, если не затрагиваются уникальные ключи.|Блокирует строку от изменений и удаления. Конфликтует со всеми, кроме `FOR KEY SHARE`.|
|**FOR UPDATE**|`SELECT ... FOR UPDATE` или `UPDATE` с изменением PK/UK.|Самая строгая. Блокирует строку от любых изменений, удалений и любых других блокировок `FOR ...`.|



### Рабочие примеры в синтаксисе PostgreSQL
#### Явное получение блокировок
```sql
-- Явная блокировка таблицы на время выполнения скрипта миграции
BEGIN;
LOCK TABLE orders IN SHARE UPDATE EXCLUSIVE MODE;
-- Здесь можно безопасно выполнять операции, которые не требуют полной блокировки
COMMIT;

-- Явная блокировка строк для предотвращения двойного списания
BEGIN;
SELECT balance FROM accounts WHERE id = 101 FOR UPDATE;
-- Теперь другая транзакция, сделавшая SELECT ... FOR UPDATE по id = 101, будет ждать COMMIT или ROLLBACK этой транзакции.
UPDATE accounts SET balance = balance - 500 WHERE id = 101;
COMMIT;
```


#### Диагностика блокировок (Как посмотреть, кто кого блокирует)
Для анализа блокировок используется системное представление `pg_locks`.

```sql
-- Запрос для поиска заблокированных сессий и тех, кто их блокирует
SELECT 
    blocked_locks.pid AS blocked_pid,
    blocked_activity.usename AS blocked_user,
    blocking_locks.pid AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query AS blocked_query,
    blocking_activity.query AS blocking_query,
    blocked_locks.mode AS lock_mode,
    blocked_locks.granted
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```


### Примеры из реальной жизни
#### Сценарий 1: Интернет-магазин (Списание товара со склада)

**Проблема:** Два пользователя одновременно покупают последний товар. **Решение:** Использование `FOR UPDATE`.
```sql
BEGIN;
-- Блокируем строку с товаром. Если второй пользователь сделает такой же запрос, он встанет в очередь.
SELECT stock_count FROM products WHERE id = 55 FOR UPDATE; 

IF stock_count > 0 THEN
    UPDATE products SET stock_count = stock_count - 1 WHERE id = 55;
    -- Создание заказа...
END IF;
COMMIT; -- Блокировка снимается, второй пользователь проходит дальше.
```

_Поведение:_ На уровне таблицы берется `ROW EXCLUSIVE`, на уровне строки `FOR UPDATE`. Другие пользователи могут читать товар (`SELECT` без `FOR UPDATE`), но не могут изменить его количество.

#### Сценарий 2: Добавление индекса на высоконагруженную таблицу (Zero-Downtime)

**Проблема:** Нужно добавить индекс на таблицу `transactions` (миллионы строк). Обычный `CREATE INDEX` берет блокировку `SHARE`, которая **блокирует все операции записи** (`INSERT/UPDATE`) на время построения индекса (может занять часы). **Решение:** Использование `CONCURRENTLY`.
```sql
CREATE INDEX CONCURRENTLY idx_transactions_user_id ON transactions(user_id);
```

_Поведение:_ PostgreSQL берет блокировку `SHARE UPDATE EXCLUSIVE` на уровне таблицы. Эта блокировка **не конфликтует** с `ROW EXCLUSIVE` (которую берут `INSERT/UPDATE`). В результате индекс строится долго, но бизнес-операции записи и чтения не прерываются ни на секунду.

#### Сценарий 3: Очистка места (VACUUM FULL)

**Проблема:** Таблица разрослась из-за мертвых кортежей (MVCC), нужно физически переписать таблицу. **Решение:** `VACUUM FULL table_name;` _Поведение:_ Берется блокировка `ACCESS EXCLUSIVE`. Таблица полностью блокируется: ни читать, ни писать в неё нельзя до конца операции. В проде на больших таблицах это делается только в окна обслуживания, либо используется `pg_repack` (который использует более мягкие блокировки).
