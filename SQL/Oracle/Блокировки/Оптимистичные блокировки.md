## Введение: Что такое оптимистичная блокировка?

**Оптимистичная блокировка (Optimistic Locking)** — это стратегия контроля параллелизма, которая предполагает, что конфликты записи в базу данных происходят редко.

В отличие от _пессимистичной_ блокировки (где мы блокируем строку в БД на время чтения и обработки, например `SELECT ... FOR UPDATE`), оптимистичная блокировка **не блокирует данные при чтении**. Вместо этого она проверяет, не изменились ли данные с момента их чтения, непосредственно перед сохранением.

**Аналогия из жизни:**

- _Пессимистичная:_ Вы взяли книгу в библиотеке, и пока вы ее читаете, она физически изъята из фонда. Никто другой не может ее взять.
- _Оптимистичная:_ Вы скачали электронную книгу, начали делать в ней пометки. Когда вы пытаетесь загрузить свои правки обратно в систему, она проверяет: "Не загрузил ли кто-то новую версию этой книги, пока вы читали?". Если да — вам предложат разрешить конфликт.


## Как это работает (Алгоритм)

Обычно реализация строится вокруг специального поля в таблице: **версии (version)** или **временной метки (timestamp)**. _Спойлер: версия лучше, об этом в нюансах._

**Алгоритм:**

1. **Чтение:** Приложение читает запись из БД вместе с ее текущей версией (например, `version = 1`).
2. **Обработка:** Пользователь вносит изменения в интерфейсе (это может занять от миллисекунд до нескольких часов).
3. **Запись (UPDATE):** Приложение отправляет запрос на обновление, добавляя в `WHERE` проверку версии:
```SQL
UPDATE table_name 
SET data = 'new_data', version = version + 1 
WHERE id = 123 AND version = 1;
```
    
4. **Проверка результата:**
    - Если обновилась **1 строка** — успех! Версия стала 2.
    - Если обновилось **0 строк** — значит, кто-то другой уже обновил эту запись (версия в БД стала 2, а мы искали 1). Это **конфликт**. Приложение должно откатить изменения и сообщить пользователю или повторить попытку.

## Лучшие практики (Best Practices)

1. **Используйте целочисленный `version`, а не `timestamp`.** Часы на разных серверах могут рассинхронизироваться (clock drift). Если два сервера обновят запись в одну миллисекунду, `timestamp` может не измениться, и проверка пройдет ложно. Инкрементный `integer` надежен на 100%.
2. **Применяйте там, где конфликты редки.** Оптимистичные блокировки идеальны для профилей пользователей, настроек, статей в CMS. Они **не подходят** для снятия денег со счета, бронирования последнего места в кино или списания товара со склада при флеш-сейле (там используйте пессимистичные блокировки или атомарные операции БД).
3. **Реализуйте механизм ретраев (Retries) с экспоненциальной задержкой.** Если конфликт произошел из-за фоновой задачи, а не пользователя, система должна автоматически повторить операцию: прочитать новую версию, применить изменения и сохранить снова.
4. **Человекопонятные сообщения об ошибках.** Если ретрай невозможен (например, пользователь редактировал форму час), не показывайте ему `500 Internal Server Error`. Верните `409 Conflict` с текстом: _"Данные были изменены кем-то другим. Пожалуйста, обновите страницу и попробуйте снова"_.
5. **Используйте возможности ORM.** Hibernate, SQLAlchemy, Entity Framework имеют встроенную поддержку оптимистичных блокировок. Не пишите велосипеды, если фреймворк уже умеет это делать "из коробки".


## Нюансы и подводные камни (Gotchas)

- **Долгие транзакции и UI:** Если пользователь открыл форму редактирования и ушел на обед, а в это время другой пользователь (или фоновый джоб) обновил запись, первый пользователь при сохранении получит ошибку. Это нормальное поведение, но UX должен это предусматривать (кнопка "Обновить данные" перед сохранением).
- **Ложные срабатывания в ORM:** Некоторые ORM обновляют поле `version`, даже если фактические данные не изменились (например, при сохранении сущности, у которой просто вызвали setter с тем же значением). Это может привести к ненужным конфликтам. Настраивайте dirty-checking в ORM.
- **Soft Deletes (Мягкое удаление):** Если вы используете флаг `is_deleted`, убедитесь, что оптимистичная блокировка учитывает и его. Иначе можно получить ситуацию, когда запись "удалена", но версия не изменилась, и кто-то успешно ее "восстановит" поверх.
- **Пакетные обновления (Batch Updates):** Если вы обновляете сразу 10 строк с оптимистичной блокировкой, и конфликт возникает для 1 строки, вам нужно откатить всю транзакцию. Обрабатывайте такие кейсы аккуратно.
- **NoSQL (MongoDB, Couchbase):** В документоориентированных БД нет транзакций в классическом понимании (хотя в MongoDB они появились). Там оптимистичная блокировка реализуется путем хранения `version` внутри самого JSON-документа и использования атомарных операций `updateOne` с условием совпадения версии.

## Рабочие примеры реализации

### Пример

```SQL
-- 1. Создаем таблицу
CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    owner_name VARCHAR(100),
    balance DECIMAL(10, 2),
    version INT DEFAULT 1 -- Поле для оптимистичной блокировки
);

INSERT INTO accounts (owner_name, balance, version) VALUES ('Alice', 100.00, 1);

-- 2. Приложение читает данные
SELECT id, balance, version FROM accounts WHERE id = 1;
-- Результат: id=1, balance=100.00, version=1

-- 3. Приложение пытается сохранить изменения (снять 20$)
-- В памяти приложения: new_balance = 80.00, original_version = 1

UPDATE accounts 
SET balance = 80.00, version = version + 1 
WHERE id = 1 AND version = 1;

-- 4. Приложение проверяет количество измененных строк (affected rows).
-- Если 0 -> бросаем исключение OptimisticLockException.
```



## Резюме урока

1. **Оптимистичная блокировка** — это проверка изменений "на выходе", а не блокировка "на входе".
2. Используйте **целочисленные версии**, а не временные метки.
3. Применяйте в системах с **низкой конкуренцией за запись** (high read / low write).
4. Всегда обрабатывайте исключения конфликтов: либо делайте **автоматические ретраи**, либо показывайте **понятный UI** пользователю.
5. Доверяйте **ORM**, но понимайте, какие SQL-запросы они генерируют под капотом.
