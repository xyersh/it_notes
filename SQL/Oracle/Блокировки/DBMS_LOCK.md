
## Введение

В Oracle Database стандартные механизмы блокировок (DML-блокировки) отлично защищают _данные_ (строки, таблицы) от одновременного изменения. Но что делать, если вам нужно защитить _логику выполнения_ или _внешний ресурс_?

Например:

- Запретить одновременный запуск одного и того же batch-процесса (джоба) из разных сессий.
- Синхронизировать доступ к внешнему файлу на сервере приложений.
- Защитить критическую секцию кода, которая не связана с изменением конкретных строк в БД.

Для этих целей используется пакет **`DBMS_LOCK`**, который предоставляет механизм **прикладных (пользовательских) блокировок** (Application Locking).


## Базовые концепции

1. **Дескриптор блокировки (Lock Handle):** Уникальный идентификатор блокировки. Может быть числом (от 1073741824 до 1999999999) или строкой, полученной через `ALLOCATE_UNIQUE`.
2. **Режимы блокировки:** Чаще всего используется `X_MODE` (эксклюзивная блокировка, аналог `TMODE=6`), но доступны и другие (Share, Row Share и т.д.), если нужно реализовать сложную логику очередей.
3. **Независимость от транзакций:** По умолчанию блокировки `DBMS_LOCK` **НЕ снимаются** при `COMMIT` или `ROLLBACK`. Они живут до тех пор, пока сессия явно их не снимет или пока сессия не будет завершена.



## Лучшие практики (Best Practices)

1. **Всегда используйте `ALLOCATE_UNIQUE` вместо жестких ID.** Это делает код самодокументируемым. Имена вроде `'APP_DAILY_SYNC_JOB'` гораздо понятнее, чем число `1073741825`.
2. **Освобождайте блокировки.** Если используется `release_on_commit => FALSE` (по умолчанию), следует **обязательно** вызвать `DBMS_LOCK.RELEASE` в блоке `EXCEPTION` и в конце успешного выполнения. Иначе блокировка "повиснет" до разрыва сессии.
3. **Используем `release_on_commit => TRUE`**, если логика вашей блокировки привязана к транзакции. Это спасет от "забытых" блокировок при нештатном завершении процедуры.
4. **Всегда задавайте `timeout`.** Никогда не оставляйте `timeout` равным `NULL` (или `DBMS_LOCK.MAXWAIT`), если только вы не хотите, чтобы сессия висела вечно в ожидании ресурса. Таймаут в 5-10 секунд обычно позволяет быстро обнаружить проблему и откатить транзакцию.
5. **Проверяйте коды возврата.** Никогда не предполагайте, что `REQUEST` прошел успешно. Всегда проверяйте, что возвращен `0`.

## Нюансы и "Подводные камни" (Pitfalls)

### 1. Блокировки не видны в стандартных представлениях V$LOCK так же, как DML

Хотя блокировки `DBMS_LOCK` отображаются в `V$LOCK` (тип `UL` - User Locks), их анализ требует понимания того, какой `ID1` и `ID2` соответствуют вашему дескриптору. Для отладки зависших сессий это может быть сложнее, чем обычные Row Exclusive (TX) блокировки.

### 2. Проблема "Забытой блокировки" (Connection Pooling)

Если ваше приложение использует пул соединений (например, WebLogic, Tomcat, UCP), сессии не умирают, а возвращаются в пул. _Если вы не вызвали `RELEASE` и не использовали `release_on_commit => TRUE`_, блокировка останется висеть на сессии. Когда эта сессия будет передана другому пользователю, он может неожиданно получить ошибку `Timeout` при запросе блокировки, хотя физически ресурс свободен. **Решение:** Строжайшая дисциплина кода или использование `release_on_commit => TRUE`.

### 3. Риск Deadlocks (Взаимных блокировок)

`DBMS_LOCK` подвержен классическим deadlock'ам. _Сессия А_ берет блокировку 1, затем просит блокировку 2. _Сессия Б_ берет блокировку 2, затем просит блокировку 1. Oracle обнаружит deadlock (обычно через несколько секунд) и вернет код `2` (Deadlock) одной из сессий, откатив её запрос. Но лучше проектировать код так, чтобы порядок запроса блокировок был строго одинаковым во всех процедурах.

### 4. Таблица SYS.DBMS_LOCK_ALLOCATED

При использовании `ALLOCATE_UNIQUE` Oracle создает записи в таблице `SYS.DBMS_LOCK_ALLOCATED`.

- Нюанс: Эта таблица может расти, если вы генерируете динамические имена блокировок с миллионами уникальных значений (например, `LOCK_` || `sequence.nextval`).
- **Правило:** Используйте `ALLOCATE_UNIQUE` только для _конечного и небольшого_ набора имен (например, имена джобов, имена файлов, ID типов сущностей). Не используйте его для блокировки каждой отдельной строки/документа!

### 5. Работа в RAC (Real Application Clusters)

`DBMS_LOCK` полностью поддерживает RAC. Блокировки синхронизируются через Global Enqueue Services (GES). Если сессия на Node 1 взяла блокировку, сессия на Node 2 будет корректно ждать или получит таймаут. Никаких дополнительных настроек не требуется.

### 6. Привилегии и безопасность

Поскольку `DBMS_LOCK` позволяет влиять на выполнение других сессий, выдача прав `EXECUTE ON DBMS_LOCK` должна быть строго ограничена. В современных версиях Oracle рекомендуется создавать "обертки" (wrapper procedures) от имени владельца (Definer's Rights), которые инкапсулируют вызовы `DBMS_LOCK`, чтобы не давать конечным пользователям прямые права на пакет.


## Шпаргалка: Коды возврата DBMS_LOCK.REQUEST

| Код   | Описание            | Действие                                          |
| ----- | ------------------- | ------------------------------------------------- |
| **0** | Успех               | Блокировка получена, можно работать.              |
| **1** | Таймаут             | Время ожидания истекло. Блокировка не получена.   |
| **2** | Deadlock            | Oracle обнаружил взаимную блокировку.             |
| **3** | Parameter error     | Неверные параметры (например, неверный режим).    |
| **4** | Already owned       | Вы уже владеете этой блокировкой в данной сессии. |
| **5** | Illegal lock handle | Неверный дескриптор блокировки.                   |


## API

### 1. Константы режимов блокировки (Lock Modes)

Используются в параметрах `lockmode` процедур `REQUEST` и `CONVERT`.

| Константа            | Значение | Название режима               | Описание (аналог в DML)                                                                |
| -------------------- | -------- | ----------------------------- | -------------------------------------------------------------------------------------- |
| `DBMS_LOCK.NL_MODE`  | 1        | Null                          | Нет блокировки. Используется для получения информации о блокировке без её установки.   |
| `DBMS_LOCK.SS_MODE`  | 2        | Row Share (Sub-Shared)        | Разделяемая блокировка строк.                                                          |
| `DBMS_LOCK.SR_MODE`  | 3        | Row Exclusive (Sub-Exclusive) | Блокировка строк на изменение.                                                         |
| `DBMS_LOCK.S_MODE`   | 4        | Share                         | Полная разделяемая блокировка.                                                         |
| `DBMS_LOCK.SRX_MODE` | 5        | Share Row Exclusive           | Разделяемая блокировка строк на изменение.                                             |
| `DBMS_LOCK.X_MODE`   | 6        | **Exclusive**                 | **Эксклюзивная блокировка.** Используется в 99% случаев для защиты критических секций. |



### ALLOCATE_UNIQUE (Процедура)

Связывает уникальное строковое имя с внутренним числовым идентификатором (дескриптором). Генерирует уникальный ID и сохраняет соответствие в системной таблице `SYS.DBMS_LOCK_ALLOCATED`.
```sql
DBMS_LOCK.ALLOCATE_UNIQUE(
   lockname        IN  VARCHAR2,
   lockhandle      OUT VARCHAR2,
   expiration_secs IN  INTEGER DEFAULT 864000 -- 10 дней
);
```
- **`lockname`**: Имя блокировки (до 128 символов). Должно быть уникальным в рамках БД.
- **`lockhandle`**: Возвращаемый уникальный дескриптор (строка до 128 символов).
- **`expiration_secs`**: Время жизни записи в словаре, если блокировка не запрашивается. По умолчанию 864000 секунд (10 дней).

### REQUEST (Функция)
Запрашивает блокировку. Имеет две перегрузки: для строкового дескриптора и для числового ID.
**Версия 1 (через дескриптор):**
```sql
DBMS_LOCK.REQUEST(
   lockhandle        IN VARCHAR2,
   lockmode          IN INTEGER  DEFAULT X_MODE,
   timeout           IN INTEGER  DEFAULT 2147483647,
   release_on_commit IN BOOLEAN  DEFAULT FALSE
) RETURN INTEGER;
```

**Версия 2 (через числовой ID):**
```sql
DBMS_LOCK.REQUEST(
   id                IN NUMBER,
   lockmode          IN INTEGER  DEFAULT X_MODE,
   timeout           IN INTEGER  DEFAULT 2147483647,
   release_on_commit IN BOOLEAN  DEFAULT FALSE
) RETURN INTEGER;
```

**Параметры:**

- **`lockhandle` / `id`**: Дескриптор или числовой ID (от 1073741824 до 1999999999).
- **`lockmode`**: Режим блокировки (см. таблицу констант).
- **`timeout`**: Максимальное время ожидания в секундах. Если `0` — не ждать, если не указано (или макс. число) — ждать бесконечно.
- **`release_on_commit`**: Если `TRUE`, блокировка автоматически снимается при `COMMIT` или `ROLLBACK`. Если `FALSE` (по умолчанию) — живет до явного `RELEASE` или разрыва сессии.

**Возвращает:** Код результата: 
- 0 = успех
- 1 = таймаут
- 2 = deadlock
- 3 = ошибка параметров
- 4 = уже заблокировано
- 5 = неверный дескриптор


### CONVERT (Функция)
Изменяет режим уже удерживаемой блокировки (например, с Share на Exclusive). Также имеет две перегрузки.

```sql
DBMS_LOCK.CONVERT(
   lockhandle IN VARCHAR2, -- или id IN NUMBER
   lockmode   IN INTEGER,
   timeout    IN INTEGER  DEFAULT 2147483647
) RETURN INTEGER;
```

- **`lockmode`**: Новый желаемый режим блокировки.
- **Возвращает:** Те же коды, что и `REQUEST`.


### RELEASE (Процедура)
Явно освобождает ранее захваченную блокировку.
```sql
DBMS_LOCK.RELEASE(lockhandle IN VARCHAR2);
-- ИЛИ
DBMS_LOCK.RELEASE(id         IN NUMBER);
```
**Примечание:** Если вы используете `release_on_commit => TRUE` в `REQUEST`, вызывать `RELEASE` не обязательно (но можно). Если `FALSE` — вызов **обязателен**.

### SLEEP (Процедура)
Приостанавливает выполнение текущей сессии на указанное время. Освобождает CPU, в отличие от циклов ожидания.
```sql
DBMS_LOCK.SLEEP(seconds IN NUMBER);
```

- **`seconds`**: Время сна в **секундах**. Поддерживает дробные значения (например, `0.5` для 500 мс) начиная с Oracle 12.2.
- **Важно:** В отличие от многих других языков/пакетов, здесь время указывается именно в секундах, а не в миллисекундах!
- _Современная альтернатива:_ Начиная с Oracle 18c, рекомендуется использовать `DBMS_SESSION.SLEEP()`, так как права на `DBMS_LOCK` часто урезают из соображений безопасности.

## Важные нюансы API

1. **Две перегрузки (Overloads):** Функции `REQUEST`, `CONVERT` и процедура `RELEASE` принимают либо строковый `lockhandle` (полученный через `ALLOCATE_UNIQUE`), либо числовой `id`. Нельзя смешивать их: если вы получили хендл через `ALLOCATE_UNIQUE`, передавайте именно его, а не пытайтесь угадать числовой ID.
2. **Безопасность и права:** Пакет `DBMS_LOCK` по умолчанию выдан только пользователю `SYS`. Для использования его в приложении необходимо:
	```sql
	   GRANT EXECUTE ON DBMS_LOCK TO <ваш_схема>;
	```

_Best Practice:_ Не давать эти права конечным пользователям. Создавайте процедуры-обертки (Wrapper) с правами владельца (`AUTHID DEFINER`), которые инкапсулируют вызовы `DBMS_LOCK`. 3. **Диапазон числовых ID:** Если вы используете числовой `id` напрямую (без `ALLOCATE_UNIQUE`), он **обязан** быть в диапазоне от `1073741824` до `1999999999`. Использование чисел вне этого диапазона вызовет ошибку. 4. **SLEEP и транзакции:** `DBMS_LOCK.SLEEP` не прерывает транзакцию. Если вы "спите" внутри незавершенной транзакции, вы продолжаете удерживать все стандартные DML-блокировки (TX), что может привести к блокированию других сессий.


## Режимы блокировок DBMS_LOCK (Руководство)

Режимы блокировок в `DBMS_LOCK` — это не просто "сильнее/слабее". Это **математическая модель совместимости**, которая определяет, могут ли несколько сессий одновременно удерживать блокировки на один и тот же ресурс.

## Ключевая концепция: Матрица совместимости

Суть режимов блокировок в том, что некоторые из них **совместимы** друг с другом (могут существовать одновременно), а некоторые — **несовместимы** (одна блокировка заставит другую ждать).

Представьте, что у вас есть один ресурс (например, файл или бизнес-процесс). Разные сессии могут запрашивать блокировки на этот ресурс в разных режимах. Oracle смотрит в матрицу совместимости и решает: "Можно ли выдать эту блокировку прямо сейчас, или нужно поставить сессию в очередь?"


### NL_MODE (Null) — Значение: 1

**Аналогия:** "Я просто смотрю на расписание, но не занимаю кабинет."
**Суть:** Это "нулевая" блокировка. Она не блокирует ресурс вообще, но позволяет **узнать**, есть ли на этот ресурс другие блокировки.
**Когда использовать:**
- Для мониторинга: "Кто сейчас работает с этим ресурсом?"
- Для проверки состояния без фактической блокировки.

**Пример:**
```sql
-- Проверяем, удерживает ли кто-то блокировку на 'DAILY_REPORT'
l_result := DBMS_LOCK.REQUEST(
  lockhandle => l_handle,
  lockmode   => DBMS_LOCK.NL_MODE, -- Просто смотрим
  timeout    => 0                  -- Не ждем вообще
);

IF l_result = 0 THEN
  DBMS_OUTPUT.PUT_LINE('Ресурс свободен или занят NL-блокировкой');
ELSIF l_result = 4 THEN
  DBMS_OUTPUT.PUT_LINE('Кто-то уже держит более сильную блокировку');
END IF;
```


### SS_MODE (Row Share / Sub-Shared) — Значение: 2

**Аналогия:** "Я читаю книгу в библиотеке. Другие тоже могут читать эту же книгу, но никто не может её забрать домой."
**Суть:** Разделяемая блокировка низкого уровня. Позволяет множеству сессий одновременно "читать" ресурс, но запрещает эксклюзивный захват.
**Когда использовать:**
- Для реализации паттерна "Множество читателей, один писатель" (Readers-Writers).
- Когда несколько процессов должны одновременно получать данные, но вы хотите запретить эксклюзивную блокировку.
**Совместимость:** Совместима с NL, SS, S. Несовместима с SR, SRX, X.

### SR_MODE (Row Exclusive / Sub-Exclusive) — Значение: 3

**Аналогия:** "Я читаю книгу и делаю в ней пометки. Другие могут читать, но не могут делать свои пометки."
**Суть:** Блокировка на чтение с намерением изменения. Позволяет другим читать (SS, S), но запрещает другим делать изменения (SR, SRX, X).
**Когда использовать:**
- Редко используется в чистом виде.
- Может применяться для защиты от одновременных изменений, когда чтение всё ещё разрешено.
**Совместимость:** Совместима с NL, SS. Несовместима с SR, S, SRX, X.

### S_MODE (Share) — Значение: 4

**Аналогия:** "Мы все собрались вокруг одного документа и читаем его вместе. Никто не может его изменить, пока мы не разойдемся."
**Суть:** Полная разделяемая блокировка. Множество сессий могут одновременно удерживать S-блокировку, но ни одна не может получить SR, SRX или X.
**Когда использовать:**
- Для защиты ресурса от изменений, когда несколько процессов должны его читать.
- Для реализации "читательских" блокировок в паттерне Readers-Writers.
**Пример (Читатель):**
```sql
-- Процесс-читатель запрашивает S-блокировку
l_result := DBMS_LOCK.REQUEST(
  lockhandle => l_handle,
  lockmode   => DBMS_LOCK.S_MODE, -- Разделяемая блокировка
  timeout    => 10
);

IF l_result = 0 THEN
  -- Читаем данные
  SELECT * INTO ... FROM critical_table;
  
  -- Освобождаем
  DBMS_LOCK.RELEASE(l_handle);
END IF;
```

**Совместимость:** Совместима с NL, SS, S. Несовместима с SR, SRX, X.

### SRX_MODE (Share Row Exclusive) — Значение: 5

**Аналогия:** "Я читаю документ и готовлю его к изменению. Другие могут читать, но не могут начать свои изменения."
**Суть:** Это самый сложный и редко используемый режим. Он позволяет другим сессиям читать (SS, S), но запрещает любые другие блокировки на изменение (SR, SRX, X).
**Когда использовать:**
- Крайне редко. Обычно, если вам нужен этот режим, лучше использовать X_MODE.
- Может применяться в сложных сценариях очередей или когда нужна тонкая настройка параллелизма.
**Совместимость:** Совместима только с NL. Несовместима со всеми остальными.

### X_MODE (Exclusive) — Значение: 6

**Аналогия:** "Я закрылся в кабинете и работаю один. Никто не может войти, пока я не закончу."

**Суть:** Эксклюзивная блокировка. Только одна сессия может удерживать X-блокировку. Все остальные режимы (кроме NL) будут ждать.

**Когда использовать:**

- **В 99% случаев.** Это ваш выбор по умолчанию.
- Для защиты критических секций кода.
- Для предотвращения параллельного выполнения batch-процессов.
- Для защиты внешних ресурсов (файлы, API-вызовы).

**Пример (Писатель):**
```sql
-- Процесс-писатель запрашивает X-блокировку
l_result := DBMS_LOCK.REQUEST(
  lockhandle => l_handle,
  lockmode   => DBMS_LOCK.X_MODE, -- Эксклюзивная блокировка
  timeout    => 10
);

IF l_result = 0 THEN
  -- Изменяем данные
  UPDATE critical_table SET ...;
  COMMIT;
  
  -- Освобождаем
  DBMS_LOCK.RELEASE(l_handle);
END IF;
```

**Совместимость:** Несовместима ни с чем (кроме NL).

|**X (6)**|✅ Да|❌ Нет|❌ Нет|

## Практические сценарии использования

### Сценарий 1: Паттерн "Множество читателей, один писатель"

У вас есть кэшируемый ресурс (например, конфигурация), который часто читается, но редко обновляется. Вы хотите разрешить параллельное чтение, но запретить параллельную запись.
```SQL
-- ЧИТАТЕЛЬ (может работать параллельно с другими читателями)
PROCEDURE read_config IS
  l_handle VARCHAR2(128);
BEGIN
  DBMS_LOCK.ALLOCATE_UNIQUE('CONFIG_CACHE', l_handle);
  
  -- S_MODE позволяет другим читателям работать одновременно
  IF DBMS_LOCK.REQUEST(l_handle, DBMS_LOCK.S_MODE, 5) = 0 THEN
    -- Читаем конфигурацию
    load_config_from_db();
    DBMS_LOCK.RELEASE(l_handle);
  END IF;
END;

-- ПИСАТЕЛЬ (работает эксклюзивно)
PROCEDURE update_config IS
  l_handle VARCHAR2(128);
BEGIN
  DBMS_LOCK.ALLOCATE_UNIQUE('CONFIG_CACHE', l_handle);
  
  -- X_MODE запрещает всем читателям и писателям работать
  IF DBMS_LOCK.REQUEST(l_handle, DBMS_LOCK.X_MODE, 10) = 0 THEN
    -- Обновляем конфигурацию
    update_config_in_db();
    DBMS_LOCK.RELEASE(l_handle);
  END IF;
END;
```

**Результат:**

- 10 читателей могут работать одновременно (S совместим с S).
- Писатель будет ждать, пока все читатели закончат.
- Читатели будут ждать, пока писатель закончит.


### Сценарий 2: Очередь задач с приоритетами
У вас есть очередь задач, и вы хотите, чтобы только один процесс забирал задачу из очереди.

```SQL
FUNCTION get_next_task RETURN NUMBER IS
  l_handle VARCHAR2(128);
  l_task_id NUMBER;
BEGIN
  DBMS_LOCK.ALLOCATE_UNIQUE('TASK_QUEUE', l_handle);
  
  -- X_MODE гарантирует, что только один процесс забирает задачу
  IF DBMS_LOCK.REQUEST(l_handle, DBMS_LOCK.X_MODE, 5) = 0 THEN
    BEGIN
      -- Забираем задачу из очереди
      SELECT task_id INTO l_task_id
      FROM task_queue
      WHERE status = 'PENDING'
      AND ROWNUM = 1
      FOR UPDATE SKIP LOCKED;
      
      UPDATE task_queue SET status = 'PROCESSING' WHERE task_id = l_task_id;
      COMMIT;
      
    EXCEPTION
      WHEN NO_DATA_FOUND THEN
        l_task_id := NULL; -- Нет задач
    END;
    
    DBMS_LOCK.RELEASE(l_handle);
    RETURN l_task_id;
  ELSE
    RETURN NULL; -- Не удалось получить блокировку
  END IF;
END;
```

### Сценарий 3: Защита от двойного запуска batch-процесса

Самый частый сценарий — использовать X_MODE для предотвращения параллельного запуска.
```SQL
PROCEDURE run_daily_report IS
  l_handle VARCHAR2(128);
  l_result NUMBER;
BEGIN
  DBMS_LOCK.ALLOCATE_UNIQUE('DAILY_REPORT_JOB', l_handle);
  
  -- Пытаемся получить X-блокировку без ожидания
  l_result := DBMS_LOCK.REQUEST(l_handle, DBMS_LOCK.X_MODE, 0);
  
  IF l_result = 0 THEN
    BEGIN
      DBMS_OUTPUT.PUT_LINE('Запуск отчета...');
      generate_daily_report();
      DBMS_OUTPUT.PUT_LINE('Отчет завершен.');
    EXCEPTION
      WHEN OTHERS THEN
        DBMS_OUTPUT.PUT_LINE('Ошибка: ' || SQLERRM);
        RAISE;
    END;
    
    DBMS_LOCK.RELEASE(l_handle);
  ELSIF l_result = 1 THEN
    DBMS_OUTPUT.PUT_LINE('Отчет уже выполняется в другой сессии. Выход.');
  ELSE
    RAISE_APPLICATION_ERROR(-20001, 'Ошибка получения блокировки: ' || l_result);
  END IF;
END;
```
## Рекомендации по выбору режима

|Сценарий|Рекомендуемый режим|Обоснование|
|---|---|---|
|Защита batch-процесса от параллельного запуска|**X_MODE (6)**|Нужна полная эксклюзивность.|
|Работа с внешним файлом|**X_MODE (6)**|Файл не поддерживает параллельную запись.|
|Кэшируемый ресурс (чтение/запись)|**S_MODE (4)** для чтения, **X_MODE (6)** для записи|Паттерн Readers-Writers.|
|Мониторинг состояния ресурса|**NL_MODE (1)**|Не нужно блокировать, только проверить.|
|Синхронизация API-вызовов|**X_MODE (6)**|API обычно не поддерживает параллельные вызовы.|
|Сложные очереди с приоритетами|**SRX_MODE (5)** или **X_MODE (6)**|Зависит от требований к параллелизму.|

---
## Резюме

1. **В 99% случаев используйте X_MODE (6).** Это ваш выбор по умолчанию для защиты критических секций.
2. **S_MODE (4)** полезен для паттерна "Множество читателей, один писатель".
3. **NL_MODE (1)** — для мониторинга без блокировки.
4. **SS, SR, SRX** — редко используются в прикладном коде. Они нужны для очень специфичных сценариев тонкой настройки параллелизма.
5. **Всегда смотрите в матрицу совместимости**, если используете не-X режимы. Это поможет понять, какие сессии смогут работать параллельно.
6. **Конвертация блокировок** (`DBMS_LOCK.CONVERT`) позволяет изменить режим уже удерживаемой блокировки без её освобождения. Это полезно, если вы начали с S_MODE, а потом поняли, что нужно X_MODE.
